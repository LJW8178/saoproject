## 기존 메모 (보존)

```html
<li>Spacial-Order</li>
                                <li>Showcase</li>
                                <li>PT</li>
                                <li>29Magazine</li>
```

## 비교 범위와 판정 기준

- 확인일: 2026-11-03
- 작성본: `1.코딩/29cm/index.html`, `style.css`
- 답지: `1.코딩/답지/29CM_구현_정답 복사본/01_섹션별/M29-01_상단/index.html`, `style.css`
- 두 HTML과 CSS 전체 및 작성본 로고 SVG를 읽고 정적으로 비교했다. 브라우저 렌더링, 실제 클릭, 외부 자원 다운로드는 검증하지 않았다.
- 답지는 1600px PC 화면과 모나미 수업 문법을 전제로 한다. 과제 일치 여부와 실무 품질은 별개로 평가한다.
- 클래스명, Flex 사용 방식, SVG 사용 자체는 오류가 아니다. 아래 개선 예시는 제안이며 원본 HTML/CSS는 수정하지 않았다.

## 2. CSS 차이와 영향

### 2-1. 기본 여백 초기화 — 수정 우선

- 작성본은 `ul, li`만 여백을 초기화한다. `body`와 `h1` 등 제목의 기본 margin은 남는다.
- 답지는 `body, ul, li { margin: 0; padding: 0; }`, 제목과 p에 `margin: 0`을 선언한다.
- 일반 브라우저의 body 기본 여백 때문에 헤더 바깥에 공간이 생길 수 있다. h1의 기본 여백도 로고 정렬 계산에 개입한다. 정확한 기본값은 브라우저 스타일에 의존한다.
- 권장: body 및 필요한 제목·문단의 여백을 명시적으로 초기화한다. 모든 요소를 무조건 초기화해야 한다는 표준은 아니다.

### 2-2. 컨테이너 너비와 가운데 배치 — 수정 우선

작성본:

```css
.m-header { padding-left: 48px; padding-right: 48px; }
.con { width: 1401px; display: flex; justify-content: center; }
```

답지:

```css
.con {
  width: 1400px;
  padding-left: 20px;
  padding-right: 20px;
  margin-left: auto;
  margin-right: auto;
  display: flex;
}
```

- `justify-content: center`는 .con 안의 자식을 정렬한다. .con 자신을 부모 가운데로 옮기는 속성이 아니다.
- 작성본은 고정 좌측 패딩에서 시작하고, 답지는 컨테이너 좌우 auto margin으로 화면 중앙에 배치한다.
- 답지의 기본 content-box 기준 컨테이너 외부 너비는 `1400 + 20 + 20 = 1440px`이다. 1600px 화면에서 콘텐츠 시작점은 `(1600 - 1440) / 2 + 20 = 100px`이다.
- 작성본은 통상적인 body margin 8px을 가정하면 콘텐츠 시작점이 `8 + 1px 테두리 + 48px 패딩 = 57px` 부근이다. 이는 코드에 근거한 예상값이며 화면 측정값은 아니다.
- 1401px과 1400px의 1px 차이만 맞추는 것으로는 해결되지 않는다. 컨테이너 정렬 방식과 패딩 소유 위치를 함께 맞춰야 한다.

### 2-3. 헤더 높이와 줄 간격 — 수정 우선

- 작성본: `.m-header`의 `height: 214px`, 위 40px·아래 20px 패딩, 1px 테두리, 세로 Flex 및 `gap: 24px`.
- 기본 content-box이므로 작성본 헤더 바깥 높이는 `214 + 40 + 20 + 2 = 276px`이다. height 214px이 최종 높이가 아니다.
- 작성본 세 줄의 지정 높이는 `28 + 48 + 28 = 104px`, 두 gap은 48px로 합계 152px이다. 지정 콘텐츠 높이 214px과 차이가 있어 아래쪽에 추가 공간이 남을 수 있다.
- 답지는 세 줄을 `76 + 84 + 76 = 236px`로 배치한다. 헤더 자체의 별도 패딩·gap·테두리는 없다.
- 개선: 답지 일치가 목적이면 줄별 높이 방식으로 맞춘다. 실무에서는 텍스트 확대·줄바꿈도 고려해 padding과 min-height 중심으로 설계할 수 있다.
- `border: 1px solid red`는 개발용 표시로 보인다. 유효한 CSS지만 완성 화면에 필요 없다면 제거한다.
- border-box는 계산을 단순하게 만드는 선택이지 필수 표준은 아니다. 적용하면 기존 width/height의 의미가 바뀌므로 답지 수치를 그대로 복사하지 않는다.

### 2-4. 로고 이미지 크기 — 수정 우선

- 작성본은 `.main-logo { width: 57px; height: 15px; }`로 h1만 제한한다. `.main-logo img`에는 크기가 없다.
- 답지는 `.logo-box img { width: 88px; }`로 이미지 자체를 제어한다.
- 작성본 SVG에는 viewBox가 있고 width/height는 없다. 부모의 width가 이미지에 자동 상속되지는 않으므로 h1의 57×15px만으로 이미지가 그 크기로 표시된다고 보장할 수 없다. 정확한 렌더링 크기는 브라우저 확인이 필요하다.
- 개선 예: `.main-logo img { width: 57px; height: auto; }`. 답지 외관을 목표로 하면 88px 기준으로 조정한다. 이미지 크기를 먼저 정하고 부모의 고정 높이 필요성도 재검토한다.

### 2-6. 정렬·호버·유지보수

- 답지는 사용자 메뉴 부모와 카테고리 줄·목록에 `align-items: center`를 준다. 작성본은 일부 내부 목록만 중앙 정렬하므로 요소 높이와 line-height에 따라 줄 안의 수직 위치가 달라질 수 있다. 실제 불일치는 화면 확인이 필요하다.
- 작성본은 가상 요소로 검은 밑줄(큰 메뉴 6px, 카테고리 4px)을 표시하고, 답지는 hover 때 주황색으로 바뀐다. 둘 다 가능한 디자인이다.
- 큰 메뉴의 `bottom: 0` 밑줄이 글자 하단과 겹칠 가능성이 있으므로 폰트 로딩 후 확인한다. 카테고리는 `top: 100%`로 링크 아래에 배치한다.
- 양쪽 모두 별도 `:focus-visible` 스타일은 없다. 기본 outline을 제거한 것은 아니므로 포커스가 무조건 안 보인다고 단정할 수 없다. 실무에서는 키보드 포커스도 의도적으로 설계하고 확인한다.
- 작성본의 `.m-nav-list > nav > ul > li > a`처럼 긴 선택자는 HTML 중첩 변경에 민감하다. 역할별 클래스나 더 짧은 선택자를 고려한다. 긴 선택자 자체가 표준 위반은 아니다.
- 작성본 `.m-nav-list > nav > ul`의 `position: relative`는 현재 a의 가상 요소 배치에는 필요하지 않다. 가상 요소의 기준은 별도로 relative인 a다. 다른 목적이 없다면 정리할 수 있다.
- 답지에는 상단 HTML에서 쓰지 않는 `.editorial-*`, `.campaign-*`, `.feed-*` 스타일이 포함돼 있다. 공유 학습 파일이라는 이유는 있으나 상단만 독립 배포한다면 불필요한 CSS를 분리할 수 있다. 작성본에 이 코드가 없다는 것은 누락 오류가 아니다.

## 3. 실무·접근성 관점에서 우선 개선할 점

### 우선순위 높음: 동작과 의미

1. 빈 href와 `#`를 실제 목적지로 연결한다. `href=""`는 현재 문서로 해석될 수 있으며 기능 없는 링크를 만드는 좋은 대안이 아니다.
2. 로그인은 이동인지 창 열기인지 결정하고 그에 맞는 a 또는 button을 사용한다. 현재 작성본에는 버튼 동작을 수행할 코드가 없다.
3. 검색이 실제 기능이라면 네이티브 button 또는 검색 form을 사용한다. div/span에 아이콘을 넣는 것만으로는 키보드 조작 가능한 컨트롤이 되지 않는다.
4. 검색 버튼에는 `aria-label="검색"` 같은 접근 가능한 이름을 제공한다. 텍스트가 이미 있는 사용자 메뉴의 장식 아이콘에는 `aria-hidden="true"`를 고려해 `favorite` 같은 아이콘용 문자열이 중복 낭독되지 않도록 한다.
5. Event / Lookbook을 메뉴로 제공하려면 링크를 넣는다. 여러 nav를 유지한다면 `aria-label="사용자 메뉴"`, `aria-label="주요 메뉴"`, `aria-label="상품 카테고리"` 등으로 구분하는 것이 좋다.

예시(기능 연결은 별도 구현 필요):

```html
<button type="button" class="search" aria-label="검색">
  <span class="material-symbols-outlined" aria-hidden="true">search</span>
</button>
```

### 우선순위 중간: 화면 크기·확대 대응

- 양쪽 모두 큰 고정 너비를 사용하고 미디어 쿼리가 없다. 답지의 PC 학습 목표에서는 의도된 제한이지만 실서비스 완성본 기준으로는 좁은 화면 대응이 부족하다.
- viewport 메타 태그만으로 반응형이 되지는 않는다. 컨테이너의 유동 너비, 메뉴 접기·줄바꿈, 내용에 맞는 높이 등을 함께 설계한다.
- WCAG 2.2 리플로우 기준은 일반적인 가로쓰기 콘텐츠에서 320 CSS px 상당 너비의 대응을 다룬다. 이 메모는 해당 기준의 정식 적합성 시험을 수행한 결과는 아니다.
- hover 효과와 함께 키보드 탐색, 포커스 표시, 텍스트 확대, 클릭 영역을 확인한다. 현재 코드만으로 모든 접근성 적합 여부를 판정하지 않는다.

### 우선순위 낮음: 관리 편의

- 선택자와 코드 포맷을 일관되게 정리한다. 클래스명 `login-but`은 유효하지만 팀 규칙에 따라 `login-button` 등으로 명확히 할 수 있다.
- 외부 폰트·아이콘이 실패해도 메뉴 의미가 전달되는지 확인한다. 텍스트가 있는 링크는 유지하고 검색 아이콘에는 별도의 이름을 둔다.
- 글꼴, 이미지 포맷, 폴더 구조, Flex 세로 배치는 프로젝트 선택이며 어느 하나만 업계 표준 정답인 것은 아니다.

## 4. 답지에서도 그대로 따르기 전에 확인할 부분

- 사용자 메뉴 세 항목이 span이어서 실제 이동이 불가능하다.
- SEARCH도 span이므로 검색 기능이나 네이티브 컨트롤이 없다.
- 카테고리 대부분이 동일한 통합본 구간으로 이동한다. 실제 쇼핑몰의 카테고리별 목적지 구현은 아니다.
- 고정 PC 너비·줄 높이만 제공하므로 모바일과 확대 대응을 추가해야 한다.
- 여러 nav에 별도의 접근 가능한 구분 이름이 없다. 별도 포커스 디자인도 검토할 수 있다.
- 이 섹션에서 사용하지 않는 메인 카드 CSS가 포함돼 있다.
- `target="_blank"`에는 새 탭 열림을 이용자에게 명확히 안내하는 방식을 검토한다. 현대 브라우저의 암묵적 noopener 동작을 무시하고 rel 부재만으로 보안 취약점이라고 단정하지 않는다.

## 5. 수정 순서 제안

1. `Spacial-Order` 오타, 링크 목적지, 로그인·검색 동작을 정리한다.
2. body·제목 여백, 컨테이너 가운데 배치, 로고 img 크기를 명시한다.
3. content-box 계산을 고려해 헤더 높이와 줄별 간격을 맞춘다.
4. 답지 기준의 폰트 크기·굵기·메뉴 간격·호버 디자인을 적용할지 결정한다.
5. 실서비스 범위라면 좁은 화면·확대·키보드 접근성을 검증한다.
